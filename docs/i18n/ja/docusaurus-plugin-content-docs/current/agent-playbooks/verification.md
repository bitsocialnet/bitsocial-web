# 検証

チェックは、変更された挙動と残っている不確実性から選びます。同じ最終状態について得られた成功の証跡は再利用し、関連する編集や失敗の後には再実行します。CI・リリース・ユーザーによる明示的な要件は引き続き適用されます。

| 変更                                                       | 適切なチェック                                                                                                                    |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 文章・コメント・フォーマットのみ                           | 差分、参照、関連するジェネレーター。アプリのビルドは不要                                                                          |
| AI ワークフローのソースや設定                              | `yarn ai-workflow:sync`、`yarn ai-workflow:check`、`yarn ai-workflow:test`。コンテキストが変わった場合は LLM インデックスを再生成 |
| 独立したヘルパーやスクリプト                               | 対象を絞った実行やフィクスチャ、影響を受けるコードの構文チェックまたは型・lint チェック                                           |
| 共有ランタイム、依存関係、ビルド、インテグレーションの変更 | 影響範囲に絞ったチェックに加え、下記の該当するビルド・型・lint チェック                                                           |
| CSS・テーマ・レイアウトのみ                                | 選んだブラウザで、影響を受けるルート・ビューポート・テーマを確認。インポート、アセット、CSS 処理が変わった場合はビルド            |
| React の state・エフェクト・パフォーマンス                 | 影響を受ける挙動と、該当する React のガイダンス。診断で具体的な懸念を解消できる場合は Doctor                                      |

## プロジェクトのチェック

- `yarn build:verify` は影響を受けるワークスペースを選択します。範囲が分かっている場合は `yarn build:about`、`yarn build:chain`、`yarn build:stats-monitor`、`yarn docs:build:verify` のいずれかを使います。
- `yarn build` は、すべてのドキュメントロケールを含む about/docs の本番フルビルドを意図的に実行します。リリース全体の検証や、その範囲に見合う変更に使います。
- `yarn lint`、`yarn typecheck`、`yarn format:check` は既存のリポジトリのゲートをカバーします。範囲の狭いスクリプト編集では、まずそのスクリプトに絞った構文・フィクスチャ・フォーマットのチェックを使います。
- マニフェストやロックファイルの変更には、`corepack yarn install`、`yarn deps:check-pinned`、`yarn deps:check-hardened` が必要です。`yarn knip` は依存関係やインポートについてのアドバイザリーなチェックです。
- ドキュメント翻訳のチェックは [translations.md](translations.md) にあります。範囲を絞ったドキュメント変更では、一括翻訳ライターを実行しないでください。

## ブラウザの証跡と所有

小さく独立したブラウザ向けの変更には Chrome を使います。共有の CSS・レイアウト・レスポンシブ対応、ブラウザ依存の API、広範なインタラクション、リリース、明示的なクロスブラウザ要件がある場合は、Firefox と WebKit も加えます。影響を受けるモバイルレイアウトやタッチ操作も対象に含めてください。ビューポートのサイズ変更だけではタッチエミュレーションになりません。例示されたものが使えると決めつけず、実際のルートとコンテンツをソースから選んでください。

`playwright-cli` は `./scripts/pw-session.sh` 経由で使います。アクティブにできるブラウザはマシン全体で 1 つです。選んだエンジンは順番に実行し、自分が所有する各セッションは、失敗した後でも名前を正確に指定して閉じます。呼び出し元が所有し、使用を許可されたセッションは、閉じずに再利用します。ブラウザの一括クリーンアップは決して使わず、所有者がはっきりしないサーバーは停止しないでください。ドキュメントのみの作業ではブラウザもサーバーも不要です。

パフォーマンスの作業では、ビューポート、コンテンツ、ネットワーク・CPU の設定、ビルドモード、計測のオーバーヘッドを揃えたうえで同じフローを比較します。観察結果と推測される原因は区別してください。こうした計測が実際の依頼に答えるものである場合は、profile スキルを使います。

## 最終的な証跡

重い検証は 1 つのエージェントが担当します。実行中のワークロードを確認し、インストール、ビルドやフルスイート、Doctor、Android・Electron の作業、ブラウザのプロファイリングは直列に実行します。実行したコマンドとその結果、具体的な制約を報告してください。データの欠落やスキップしたエンジンは合格ではありません。ツール用のフィクスチャが検証するのは形式と仕組みであり、アプリによるエンドツーエンドの検出やモデルの判断の質ではありません。

## React の自動チェック

`yarn agent:verify` は、選択されたビルドを実行した後、`yarn doctor:check` と `yarn perf:check` を実行します。`perf:check` にはコレクターの互換性チェックと、意図的なリグレッションを使ったセルフテストが含まれるため、CI でもエージェントの検証経路でも、別途 `perf:test` を実行する必要はありません。固定バージョンのブラウザツールは `yarn perf:install` で一度だけインストールします (Linux の CI では `--with-deps` を付けます)。関連する範囲を一通り実行した後に絞り込んで再実行する場合は、ターゲットやシナリオのフィルターを使います。シナリオごとのバジェットは `scripts/react-perf/config.mjs` に明示されています。正当な理由のあるベースライン変更を検討する前に、証跡を残し、リグレッションを修正してください。通常の本番ビルドには Bippy が含まれません。公式の React プロファイリング計測は、別の `build:profile:*` コマンドが提供します。

about の `apps-search` シナリオは、1 文字ごとに確定した URL と入力値によってペースが制御されています。このシナリオの合格が示すのはその確定済みクエリの流れであり、高速なタイピングに対する応答性ではありません。文字の取りこぼしや入力の応答性を評価する場合は、別途高速入力の再現を用意してください。
