# Перевірка

Добирайте перевірки відповідно до зміненої поведінки та невизначеності, що лишається. Повторно використовуйте успішні докази для того самого кінцевого стану; запускайте перевірки знову після релевантних правок або збоїв. Явні вимоги CI, релізу чи користувача й далі діють.

| Зміна                                                                  | Доречні перевірки                                                                                                             |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Лише текст, коментарі чи форматування                                  | Діф, посилання, відповідні генератори; без збірки застосунку                                                                  |
| Джерела чи конфігурація робочого процесу AI                            | `yarn ai-workflow:sync`, `yarn ai-workflow:check`, `yarn ai-workflow:test`; перегенеруйте індекси LLM, якщо змінився контекст |
| Ізольований допоміжний модуль чи скрипт                                | Цільовий запуск/фікстури та перевірки синтаксису або типів/лінту для зачепленого коду                                         |
| Зміна спільного середовища виконання, залежності, збірки чи інтеграції | Цільові перевірки зачепленого коду плюс відповідні перевірки збірки/типів/лінту, наведені нижче                               |
| Лише CSS, тема чи макет                                                | Зачеплені маршрути/області перегляду/теми в обраних браузерах; збірка, якщо змінилися імпорти, ресурси чи обробка CSS         |
| Стан, ефекти чи продуктивність React                                   | Зачеплена поведінка й застосовні рекомендації щодо React; Doctor, коли діагностика відповідає на конкретне питання            |

## Перевірки проєкту

- `yarn build:verify` обирає зачеплену робочу область. Для відомого обсягу використовуйте `yarn build:about`, `yarn build:chain`, `yarn build:stats-monitor` або `yarn docs:build:verify`.
- `yarn build` свідомо запускає повну продакшн-збірку about/docs, зокрема всіх локалей документації. Використовуйте її для перевірки всього релізу або для змін, які виправдовують такий обсяг.
- `yarn lint`, `yarn typecheck` і `yarn format:check` охоплюють наявні гейти репозиторію; для вузької правки скрипту спершу використовуйте його цільові перевірки синтаксису/фікстур/форматування.
- Зміни маніфесту чи lock-файлу вимагають `corepack yarn install`, `yarn deps:check-pinned` і `yarn deps:check-hardened`. `yarn knip` має дорадчий характер щодо залежностей та імпортів.
- Перевірки перекладів документації описано в [translations.md](translations.md); не запускайте скрипт масового запису перекладів для цільової зміни в документації.

## Докази з браузера та володіння сесіями

Для невеликих ізольованих змін у браузері використовуйте Chrome. Додавайте Firefox і WebKit для спільних CSS/макета/адаптивності, чутливих до браузера API, широких взаємодій, релізів або явних кросбраузерних критеріїв. Охоплюйте зачеплені мобільні макети й поведінку дотиків. Сама лише зміна розміру області перегляду не є емуляцією дотиків. Обирайте реальні маршрути й вміст на основі вихідного коду, а не припускайте, що приклади доступні.

Використовуйте `playwright-cli` через `./scripts/pw-session.sh`. На всій машині одночасно активний лише один браузер; вибрані рушії запускаються послідовно, і кожна власна сесія закривається за точною назвою навіть після збою. Повторно використовуйте дозволену сесію, що належить тому, хто вас викликав, не закриваючи її. Ніколи не застосовуйте глобальне прибирання браузерів і не зупиняйте сервер, власник якого незрозумілий. Для роботи лише з документацією браузер чи сервер не потрібні.

Для роботи з продуктивністю порівнюйте той самий сценарій з еквівалентними областю перегляду, вмістом, налаштуваннями мережі/CPU, режимом збірки та накладними витратами на вимірювання. Розрізняйте спостереження й імовірні причини. Використовуйте навичку профілювання, коли ці вимірювання відповідають на фактичний запит.

## Підсумкові докази

Важкі перевірки належать одному агентові. Перевіряйте активні навантаження й виконуйте послідовно встановлення, збірки/повні набори тестів, Doctor, роботу з Android/Electron і профілювання в браузері. Повідомляйте команди/результати та конкретні обмеження; брак даних чи пропущений рушій не є успішним результатом. Фікстури інструментарію перевіряють формати й механіку, а не наскрізне виявлення застосунком чи якість рішень моделі.

## Автоматичні перевірки React

`yarn agent:verify` запускає вибрані збірки, а потім `yarn doctor:check` і `yarn perf:check`. `perf:check` містить самоперевірку сумісності колектора та навмисної регресії, тож ні CI, ні шлях перевірки агентом не потребують окремого проходу `perf:test`. Один раз установіть закріплений браузерний інструментарій через `yarn perf:install` (`--with-deps` у Linux CI). Для цільових повторних запусків після повного релевантного проходу використовуйте фільтри цілей/сценаріїв. Бюджети сценаріїв явно задано в `scripts/react-perf/config.mjs`; зберігайте докази й виправляйте регресію, перш ніж розглядати обґрунтовану зміну базової лінії. Звичайні продакшн-збірки не містять Bippy; окремі команди `build:profile:*` додають офіційне інструментування профілювання React.

Сценарій `apps-search` сайту about після кожного символу чекає, доки значення в URL і полі введення застосується, і лише тоді вводить наступний. Його успішний результат покриває саме цю послідовність застосованих запитів, а не чутливість до швидкого набору. Щоб оцінити втрату символів чи чутливість введення, використовуйте окреме відтворення зі швидким введенням.
