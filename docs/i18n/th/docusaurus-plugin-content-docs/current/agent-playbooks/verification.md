# การตรวจสอบ

เลือกการตรวจตามพฤติกรรมที่เปลี่ยนไปและความไม่แน่นอนที่ยังเหลืออยู่ ใช้หลักฐานที่ผ่านแล้วซ้ำได้เมื่อสถานะสุดท้ายยังเป็นสถานะเดียวกัน และรันใหม่หลังการแก้ไขที่เกี่ยวข้องหรือหลังเกิดความล้มเหลว ข้อกำหนดที่ระบุไว้ชัดเจนจาก CI/รีลีส/ผู้ใช้ยังคงมีผลบังคับ

| การเปลี่ยนแปลง                                                       | การตรวจที่เหมาะสม                                                                                                      |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| เฉพาะข้อความ/คอมเมนต์/การจัดรูปแบบ                                   | diff การอ้างอิง และสคริปต์สร้างไฟล์ที่เกี่ยวข้อง โดยไม่ต้องบิลด์แอป                                                    |
| ซอร์สหรือการกำหนดค่าของเวิร์กโฟลว์ AI                                | `yarn ai-workflow:sync`, `yarn ai-workflow:check`, `yarn ai-workflow:test` และสร้างดัชนี LLM ใหม่เมื่อคอนเท็กซ์เปลี่ยน |
| ฟังก์ชันช่วยหรือสคริปต์ที่แยกเป็นอิสระ                               | การเรียกใช้/ฟิกซ์เจอร์แบบเจาะจง พร้อมการตรวจไวยากรณ์หรือ type/lint ของโค้ดที่ได้รับผลกระทบ                             |
| การเปลี่ยนแปลงรันไทม์ที่ใช้ร่วมกัน, dependency, บิลด์ หรือการผสานรวม | การตรวจเฉพาะส่วนที่ได้รับผลกระทบ พร้อมการตรวจ build/type/lint ที่เกี่ยวข้องด้านล่าง                                    |
| เฉพาะ CSS/ธีม/เลย์เอาต์                                              | เส้นทาง/วิวพอร์ต/ธีมที่ได้รับผลกระทบในเบราว์เซอร์ที่เลือก และบิลด์เมื่อ import, asset หรือการประมวลผล CSS เปลี่ยน      |
| สถานะ/effect/ประสิทธิภาพของ React                                    | พฤติกรรมที่ได้รับผลกระทบและแนวทาง React ที่ใช้ได้ ใช้ Doctor เมื่อผลวินิจฉัยช่วยไขข้อกังวลที่เป็นรูปธรรม               |

## การตรวจของโปรเจกต์

- `yarn build:verify` เลือกเวิร์กสเปซที่ได้รับผลกระทบให้เอง หากรู้ขอบเขตอยู่แล้ว ให้ใช้ `yarn build:about`, `yarn build:chain`, `yarn build:stats-monitor` หรือ `yarn docs:build:verify`
- `yarn build` ตั้งใจรันบิลด์โปรดักชันของ about/docs แบบเต็ม รวมถึงเอกสารทุกภาษา ใช้คำสั่งนี้สำหรับการตรวจสอบระดับทั้งรีลีส หรือการเปลี่ยนแปลงที่สมควรใช้ขอบเขตนั้น
- `yarn lint`, `yarn typecheck` และ `yarn format:check` ครอบคลุมด่านตรวจที่มีอยู่แล้วของ repo สำหรับการแก้สคริปต์ในขอบเขตแคบ ให้ใช้การตรวจไวยากรณ์/ฟิกซ์เจอร์/รูปแบบที่เจาะจงกับสคริปต์นั้นก่อน
- การเปลี่ยนแปลง manifest/lock ต้องรัน `corepack yarn install`, `yarn deps:check-pinned` และ `yarn deps:check-hardened` ส่วน `yarn knip` เป็นเพียงการตรวจเชิงคำแนะนำสำหรับ dependency/import
- การตรวจงานแปลเอกสารอยู่ใน [translations.md](translations.md) อย่ารันตัวเขียนงานแปลแบบเหมารวมสำหรับการเปลี่ยนแปลงเอกสารที่เจาะจง

## หลักฐานจากเบราว์เซอร์และความเป็นเจ้าของ

ใช้ Chrome สำหรับการเปลี่ยนแปลงเล็ก ๆ ด้านเบราว์เซอร์ที่แยกเป็นส่วน ๆ เพิ่ม Firefox และ WebKit เมื่อเป็น CSS/เลย์เอาต์/การตอบสนองต่อขนาดหน้าจอที่ใช้ร่วมกัน, API ที่ไวต่อความแตกต่างของเบราว์เซอร์, การโต้ตอบในวงกว้าง, รีลีส หรือเกณฑ์ข้ามเบราว์เซอร์ที่ระบุไว้ชัดเจน รวมเลย์เอาต์มือถือ/พฤติกรรมการสัมผัสที่ได้รับผลกระทบด้วย การปรับขนาดวิวพอร์ตอย่างเดียวไม่ใช่การจำลองการสัมผัส เลือกเส้นทางและเนื้อหาจริงจากซอร์สโค้ด แทนที่จะสันนิษฐานว่ามีตัวอย่างพร้อมใช้งาน

ใช้ `playwright-cli` ผ่าน `./scripts/pw-session.sh` ทั้งเครื่องมีเบราว์เซอร์ทำงานอยู่ได้เพียงตัวเดียว เอนจินที่เลือกจะรันทีละตัว และแต่ละเซสชันที่ตนเป็นเจ้าของจะถูกปิดอย่างเจาะจงตามชื่อแม้หลังเกิดความล้มเหลว ใช้เซสชันที่ผู้เรียกเป็นเจ้าของและได้รับอนุญาตแล้วซ้ำได้โดยไม่ต้องปิด ห้ามใช้การเก็บกวาดเบราว์เซอร์แบบทั้งระบบ หรือหยุดเซิร์ฟเวอร์ที่ไม่ชัดเจนว่าใครเป็นเจ้าของ งานที่เป็นเอกสารล้วนไม่จำเป็นต้องใช้เบราว์เซอร์/เซิร์ฟเวอร์

สำหรับงานด้านประสิทธิภาพ ให้เปรียบเทียบโฟลว์เดียวกันโดยใช้วิวพอร์ต เนื้อหา การตั้งค่าเครือข่าย/CPU โหมดบิลด์ และโอเวอร์เฮดของการวัดที่เทียบเท่ากัน แยกสิ่งที่สังเกตได้ออกจากสาเหตุที่สงสัย ใช้สกิล profile เมื่อการวัดเหล่านี้ตอบคำขอที่แท้จริง

## หลักฐานขั้นสุดท้าย

เอเจนต์เพียงตัวเดียวเป็นเจ้าของการตรวจสอบที่หนัก ตรวจดูภาระงานที่กำลังทำงานอยู่ แล้วรันการติดตั้ง บิลด์/ชุดทดสอบเต็ม Doctor งาน Android/Electron และการโปรไฟล์เบราว์เซอร์ทีละอย่างตามลำดับ รายงานคำสั่ง/ผลลัพธ์และข้อจำกัดที่เฉพาะเจาะจง ข้อมูลที่ขาดหายหรือเอนจินที่ถูกข้ามไม่นับเป็นผลที่ผ่าน ฟิกซ์เจอร์ของเครื่องมือยืนยันรูปแบบและกลไกเท่านั้น ไม่ได้ยืนยันการค้นพบโดยแอปแบบ end-to-end หรือคุณภาพการตัดสินใจของโมเดล

## การตรวจ React อัตโนมัติ

`yarn agent:verify` รันบิลด์ที่เลือกไว้ แล้วตามด้วย `yarn doctor:check` และ `yarn perf:check` โดย `perf:check` รวมการทดสอบตัวเองด้านความเข้ากันได้ของตัวเก็บข้อมูลและการถดถอยที่จงใจสร้างขึ้นไว้แล้ว ทั้ง CI และเส้นทางการตรวจสอบของเอเจนต์จึงไม่ต้องรัน `perf:test` แยกอีกรอบ ติดตั้งเครื่องมือเบราว์เซอร์ที่ปักหมุดเวอร์ชันไว้เพียงครั้งเดียวด้วย `yarn perf:install` (ใช้ `--with-deps` ใน CI บน Linux) ใช้ตัวกรองเป้าหมาย/สถานการณ์ทดสอบสำหรับการรันซ้ำแบบเจาะจงหลังจากรันรอบเต็มที่เกี่ยวข้องแล้ว งบประมาณของแต่ละสถานการณ์ทดสอบระบุไว้ชัดเจนใน `scripts/react-perf/config.mjs` ให้เก็บหลักฐานไว้และแก้การถดถอยก่อนพิจารณาเปลี่ยน baseline ที่มีเหตุผลรองรับ บิลด์โปรดักชันทั่วไปไม่มี Bippy ส่วนคำสั่ง `build:profile:*` ที่แยกออกมาจะใส่เครื่องมือวัดสำหรับการโปรไฟล์ React อย่างเป็นทางการให้

สถานการณ์ทดสอบ `apps-search` ของเว็บ about เดินจังหวะตามค่า URL/อินพุตที่ commit แล้วของแต่ละตัวอักษร ผลที่ผ่านจึงครอบคลุมลำดับคำค้นที่ commit แล้วนั้น ไม่ใช่การตอบสนองเมื่อพิมพ์อย่างรวดเร็ว ให้ใช้การจำลองปัญหาด้วยการป้อนข้อมูลอย่างรวดเร็วแยกต่างหาก เมื่อประเมินการสูญหายของตัวอักษรหรือการตอบสนองต่ออินพุต
