# راستی‌آزمایی

بررسی‌ها را بر اساس رفتاری که تغییر کرده و عدم‌قطعیتی که باقی مانده انتخاب کنید. شواهد موفق را برای همان وضعیت نهایی دوباره به کار ببرید؛ پس از ویرایش‌ها یا شکست‌های مرتبط، دوباره اجرا کنید. الزامات صریح CI، انتشار نسخه یا کاربر همچنان پابرجاست.

| تغییر                                                 | بررسی‌های مناسب                                                                                                                     |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| فقط متن، توضیحات کد یا قالب‌بندی                      | دیف، ارجاع‌ها، مولدهای مرتبط؛ بدون ساخت اپ                                                                                          |
| منابع یا پیکربندی گردش کار AI                         | `yarn ai-workflow:sync`، `yarn ai-workflow:check`، `yarn ai-workflow:test`؛ وقتی کانتکست تغییر کرده، نمایه‌های LLM را بازتولید کنید |
| اسکریپت یا تابع کمکی مستقل                            | فراخوانی یا فیکسچرهای متمرکز و بررسی نحو یا نوع/لینت برای کد متأثر                                                                  |
| تغییر در رانتایم مشترک، وابستگی، ساخت یا یکپارچه‌سازی | بررسی‌های متمرکز بخش‌های متأثر به‌علاوه بررسی‌های مرتبط ساخت/نوع/لینت در ادامه                                                      |
| فقط CSS، تم یا چیدمان                                 | مسیرها، viewportها و تم‌های متأثر در مرورگرهای منتخب؛ ساخت، وقتی ایمپورت‌ها، دارایی‌ها یا پردازش CSS تغییر کرده است                 |
| وضعیت، افکت‌ها یا کارایی React                        | رفتار متأثر و راهنمای مرتبط React؛ اجرای Doctor وقتی تشخیص‌های آن به یک نگرانی مشخص پاسخ می‌دهد                                     |

## بررسی‌های پروژه

- `yarn build:verify` فضای کاری متأثر را انتخاب می‌کند. برای دامنه‌ای مشخص از `yarn build:about`، `yarn build:chain`، `yarn build:stats-monitor` یا `yarn docs:build:verify` استفاده کنید.
- `yarn build` عمداً ساخت کامل تولیدی about/docs را، با همه زبان‌های مستندات، اجرا می‌کند. از آن برای اعتبارسنجی در سطح کل انتشار یا برای تغییراتی استفاده کنید که چنین دامنه‌ای را توجیه می‌کنند.
- `yarn lint`، `yarn typecheck` و `yarn format:check` دروازه‌های موجود مخزن را پوشش می‌دهند؛ برای ویرایش محدود یک اسکریپت، ابتدا بررسی‌های متمرکز نحو/فیکسچر/قالب‌بندی همان اسکریپت را اجرا کنید.
- تغییر در مانیفست یا فایل قفل به `corepack yarn install`، `yarn deps:check-pinned` و `yarn deps:check-hardened` نیاز دارد. `yarn knip` برای وابستگی‌ها و ایمپورت‌ها جنبه مشورتی دارد.
- بررسی‌های ترجمه مستندات در [translations.md](translations.md) آمده است؛ برای یک تغییر متمرکز در مستندات، اسکریپت نوشتن انبوه ترجمه‌ها را اجرا نکنید.

## شواهد مرورگری و مالکیت

برای تغییرات کوچک و مجزای مرورگری از Chrome استفاده کنید. برای CSS، چیدمان یا واکنش‌گرایی مشترک، APIهای حساس به مرورگر، تعامل‌های گسترده، انتشار نسخه‌ها یا معیارهای صریح چندمرورگری، Firefox و WebKit را هم اضافه کنید. چیدمان‌های موبایل و رفتار لمسیِ متأثر را هم پوشش دهید. تغییر اندازه viewport به‌تنهایی شبیه‌سازی لمس نیست. مسیرها و محتوای واقعی را از روی کد منبع انتخاب کنید، نه با این فرض که نمونه‌ها در دسترس‌اند.

از `playwright-cli` از طریق `./scripts/pw-session.sh` استفاده کنید. در کل ماشین فقط یک مرورگر فعال است؛ موتورهای انتخاب‌شده پشت سر هم اجرا می‌شوند و هر نشستی که دقیقاً متعلق به شماست، حتی پس از شکست، بسته می‌شود. نشستی را که متعلق به فراخواننده است و استفاده از آن مجاز شده، بدون بستن دوباره به کار ببرید. هرگز از پاکسازی سراسری مرورگرها استفاده نکنید و سروری را که مالکیتش روشن نیست متوقف نکنید. برای کار صرفاً مستنداتی به مرورگر یا سرور نیازی نیست.

در کار روی کارایی، همان جریان را با viewport، محتوا، تنظیمات شبکه/CPU، حالت ساخت و سربار اندازه‌گیری هم‌ارز مقایسه کنید. مشاهدات را از علت‌های احتمالی جدا کنید. وقتی این اندازه‌گیری‌ها به درخواست واقعی پاسخ می‌دهند، از مهارت پروفایل‌گیری استفاده کنید.

## شواهد نهایی

راستی‌آزمایی سنگین بر عهده یک ایجنت است. بارهای کاری فعال را بررسی کنید و نصب‌ها، ساخت‌ها و مجموعه‌آزمون‌های کامل، Doctor، کار روی Android/Electron و پروفایل‌گیری مرورگر را پشت سر هم اجرا کنید. فرمان‌ها، نتایج آن‌ها و محدودیت‌های مشخص را گزارش دهید؛ داده‌ای که در دست نیست یا موتوری که از آن صرف‌نظر شده، نتیجه موفق به حساب نمی‌آید. فیکسچرهای ابزارها قالب‌ها و سازوکارها را راستی‌آزمایی می‌کنند، نه کشف سرتاسری در اپ یا کیفیت تصمیم‌گیری مدل را.

## بررسی‌های خودکار React

`yarn agent:verify` ساخت‌های انتخاب‌شده را اجرا می‌کند و پس از آن `yarn doctor:check` و `yarn perf:check` را. `perf:check` آزمون خودکار سازگاری گردآورنده و رگرسیون عمدی را در بر دارد، پس نه CI و نه مسیر راستی‌آزمایی ایجنت به اجرای جداگانه `perf:test` نیاز ندارند. ابزارهای مرورگری پین‌شده را یک بار با `yarn perf:install` نصب کنید (`--with-deps` در CI روی Linux). پس از یک اجرای کامل مرتبط، برای اجراهای دوباره متمرکز از فیلترهای هدف/سناریو استفاده کنید. بودجه‌های سناریوها به‌صراحت در `scripts/react-perf/config.mjs` تعریف شده‌اند؛ پیش از آنکه تغییر موجهی در خط پایه را در نظر بگیرید، شواهد را حفظ کنید و رگرسیون را برطرف کنید. ساخت‌های تولیدی معمولی Bippy را ندارند؛ فرمان‌های جداگانه `build:profile:*` ابزارگذاری رسمی پروفایل‌گیری React را فراهم می‌کنند.

سناریوی `apps-search` سایت about با مقادیر URL/ورودیِ کامیت‌شده برای هر کاراکتر، گام‌به‌گام پیش می‌رود. نتیجه موفق آن فقط همان توالی پرس‌وجوهای کامیت‌شده را پوشش می‌دهد، نه پاسخ‌گویی هنگام تایپ سریع را. برای ارزیابی از دست رفتن کاراکترها یا پاسخ‌گویی ورودی، یک بازتولید جداگانه با ورودی سریع به کار ببرید.
