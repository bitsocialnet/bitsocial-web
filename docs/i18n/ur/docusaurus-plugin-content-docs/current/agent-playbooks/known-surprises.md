# معلوم حیران کن باتیں

یہ فائل اس ریپوزٹری سے مخصوص اُن اُلجھن کے مقامات کا ریکارڈ رکھتی ہے جن کی وجہ سے ایجنٹوں سے غلطیاں ہوئیں۔

## اندراج کا معیار

اندراج صرف اُسی صورت میں شامل کریں جب درج ذیل تمام باتیں درست ہوں:

- یہ اسی ریپوزٹری سے مخصوص ہو (عمومی مشورہ نہ ہو)۔
- مستقبل کے ایجنٹوں کے ساتھ اس کے دوبارہ پیش آنے کا امکان ہو۔
- اس کا کوئی ٹھوس تدارک موجود ہو جس پر عمل کیا جا سکے۔

اگر یقین نہ ہو تو اندراج شامل کرنے سے پہلے ڈویلپر سے پوچھ لیں۔

## اندراج کا سانچہ

```md
### [Short title]

- **Date:** YYYY-MM-DD
- **Observed by:** agent name or contributor
- **Context:** where/when it happened
- **What was surprising:** concrete unexpected behavior
- **Impact:** what went wrong or could go wrong
- **Mitigation:** exact step future agents should take
- **Status:** confirmed | superseded
```

### Vercel ایپ کے پروڈکشن ڈومینز واپس Git master ڈیپلائمنٹس کی طرف کھسک سکتے ہیں

- **تاریخ:** 2026-04-28
- **مشاہدہ کرنے والا:** Tommaso + Codex
- **سیاق و سباق:** Bitsocial Web کی ایپ ڈائریکٹری میں Seedit اور 5chan ایپ مررز کی تصدیق۔
- **حیرت کی بات کیا تھی:** Vercel کے `seedit` اور `5chan` پروجیکٹس میں `gitProviderOptions.createDeployments = "enabled"` سیٹ تھا، اس لیے GitHub پر `master` کے پُش پروڈکشن ڈومینز تک پہنچا دیے جاتے تھے، حالانکہ ریپو کی پالیسی کے مطابق پروڈکشن ایپ مررز کو صرف ریلیز آرٹیفیکٹس سرو کرنے چاہئیں۔
- **اثر:** ایپ ڈائریکٹری کے تصدیق شدہ مرر بیجز غلط ہو سکتے ہیں، کیونکہ پروڈکشن ڈومینز اُس GitHub ریلیز ZIP کے بجائے تازہ ترین ڈیولپمنٹ کمٹ سرو کرتے ہیں جس کی `index.html` کا ہیش `about/src/lib/apps-data.ts` میں درج ہے۔
- **تدارک:** مرر تصدیق کا میٹا ڈیٹا شامل یا تازہ کرنے سے پہلے `vercel api /v9/projects/<project-id>` کے ذریعے Vercel پروجیکٹ دیکھیں اور `gitProviderOptions.createDeployments = "disabled"` کی تصدیق کریں۔ ریلیز ZIP کا مواد `vercel deploy --prebuilt --prod` سے ڈیپلائے کریں اور ڈیولپمنٹ ڈیپلائمنٹس کے لیے `seedit-omega.vercel.app` یا `5chan-omega.vercel.app` استعمال کریں۔
- **حیثیت:** تصدیق شدہ

### Portless 0.11 پرانی پراکسی حالت دوبارہ استعمال کرتا ہے، جب تک لانچر HTTPS پر مجبور نہ کرے

- **تاریخ:** 2026-04-28
- **مشاہدہ کرنے والا:** Tommaso + Codex
- **سیاق و سباق:** معمول کے `yarn start` فلو کو پرانے پراکسی URL `http://bitsocial.localhost:1355` سے اَپ گریڈ کر کے نئے کینونیکل URL پر لے جانا: `https://bitsocial.localhost`.
- **حیرت کی بات کیا تھی:** `portless@0.11.1` انسٹال ہونے کے باوجود Portless نے موجودہ `~/.portless/proxy.port = 1355` HTTP پراکسی ہی دوبارہ استعمال کی اور پرانا `:1355` والا URL چھاپا۔
- **اثر:** پیکیج ورژن اور دستاویزات اپ ڈیٹ کرنا کافی نہیں؛ جب کسی کنٹریبیوٹر کے ہاں پرانی Portless حالت چل رہی ہو تو `yarn start` اب بھی پرانا URL بتا اور استعمال کر سکتا ہے۔
- **تدارک:** اسٹارٹ اسکرپٹس کو ایسا ہی رکھیں کہ وہ ایپ روٹس رجسٹر کرنے سے پہلے Portless HTTPS پراکسی کو صراحتاً پورٹ `443` پر شروع کریں، تاکہ رن ٹائم فلو محفوظ شدہ `1355` حالت وراثت میں لینے کے بجائے اس سے آگے نکل جائے۔
- **حیثیت:** تصدیق شدہ

- **اثر:** ڈیو سرور ٹھیک چل رہا ہو تب بھی براؤزر جانچ ناکام ہو سکتی ہے یا غلط ہدف کی توثیق کر سکتی ہے۔
- **تدارک:** پہلے `https://bitsocial.localhost` استعمال کریں۔ اسے صرف اُس وقت `PORTLESS=0 corepack yarn start` سے بائی پاس کریں جب آپ کو واقعی براہِ راست Vite پورٹ درکار ہو۔

### طے شدہ Portless ایپ نام Bitsocial Web ورک ٹریز کے درمیان ٹکرا جاتے ہیں

- **تاریخ:** 2026-03-30
- **مشاہدہ کرنے والا:** Codex
- **سیاق و سباق:** ایک Bitsocial Web ورک ٹری میں `yarn start` چلانا جب کہ دوسرا ورک ٹری پہلے ہی Portless کے ذریعے سرو کر رہا ہو
- **حیرت کی بات کیا تھی:** ہر ورک ٹری میں لفظی Portless ایپ نام `bitsocial` استعمال کرنے سے خود روٹ ٹکرا جاتا ہے، چاہے پیچھے موجود پورٹس مختلف ہی ہوں، اس لیے دوسرا پراسیس ناکام ہو جاتا ہے کیونکہ `bitsocial.localhost` پہلے سے رجسٹرڈ ہوتا ہے۔
- **اثر:** متوازی Bitsocial Web برانچیں ایک دوسرے کو روک سکتی ہیں، حالانکہ Portless کا مقصد ہی انہیں محفوظ طریقے سے ساتھ ساتھ چلانا ہے۔
- **تدارک:** Portless کے آغاز کو `scripts/start-dev.mjs` کے پیچھے رکھیں، جو اب کینونیکل صورت سے باہر برانچ کے دائرے والا `*.bitsocial.localhost` روٹ استعمال کرتا ہے اور جب سادہ `bitsocial.localhost` نام پہلے سے مصروف ہو تو برانچ کے دائرے والے روٹ پر چلا جاتا ہے۔

- **سیاق و سباق:** دوسرے مقامی ریپوز اور ایجنٹوں کے ساتھ ساتھ `yarn start` چلانا
- **حیرت کی بات کیا تھی:** روٹ ڈیو کمانڈ دستاویزات کا ورک اسپیس `docusaurus start --port 3001` کے ساتھ چلاتی تھی، اس لیے جب بھی کوئی دوسرا پراسیس پہلے سے `3001` پر قابض ہوتا، پورا ڈیو سیشن ناکام ہو جاتا تھا، حالانکہ مرکزی ایپ پہلے ہی Portless استعمال کرتی تھی۔
- **اثر:** `yarn start` ویب پراسیس کو بوٹ ہوتے ہی ختم کر سکتا تھا، اور محض دستاویزات کے پورٹ ٹکراؤ کی وجہ سے غیر متعلقہ مقامی کام میں خلل پڑ جاتا تھا۔
- **تدارک:** دستاویزات کے آغاز کو `yarn start:docs` کے پیچھے رکھیں، جو اب Portless کے ساتھ `scripts/start-docs.mjs` استعمال کرتا ہے تاکہ دیے گئے خالی پورٹ کا لحاظ رکھے یا براہِ راست چلائے جانے پر اگلے دستیاب پورٹ پر چلا جائے۔
- **حیثیت:** تصدیق شدہ

### ورک ٹری شیلز ریپو کے پن کیے گئے Node ورژن سے چوک سکتے ہیں

- **تاریخ:** 2026-04-03
- **مشاہدہ کرنے والا:** Codex
- **سیاق و سباق:** `.claude/worktrees/*` جیسے Git ورک ٹریز یا ساتھ والے ورک ٹری چیک آؤٹس میں `yarn start` چلانا
- **حیرت کی بات کیا تھی:** بعض ورک ٹری شیلز `node` اور `yarn node` کو Homebrew کے Node `25.2.1` پر حل کرتے تھے، حالانکہ ریپو `.nvmrc` میں `22.12.0` پن کرتا ہے، چنانچہ `yarn start` خاموشی سے ڈیو لانچرز کو غلط رن ٹائم پر چلا سکتا تھا۔
- **اثر:** ڈیو سرور کا رویہ مرکزی چیک آؤٹ اور ورک ٹریز کے درمیان مختلف ہو سکتا ہے، جس سے بگز کو دوبارہ پیدا کرنا مشکل ہو جاتا ہے اور ریپو کا متوقع Node 22 ٹول چین بھی ٹوٹ جاتا ہے۔
- **تدارک:** ڈیو لانچرز کو `scripts/start-dev.mjs` اور `scripts/start-docs.mjs` کے پیچھے رکھیں، جو اب موجودہ شیل کے غلط ورژن پر ہونے کی صورت میں `.nvmrc` والی Node بائنری کے تحت خود کو دوبارہ چلا لیتے ہیں۔ شیل سیٹ اپ میں پھر بھی `nvm use` کو ترجیح دی جانی چاہیے۔
- **حیثیت:** تصدیق شدہ

### کثیر لسانی دستاویزات کا پیش منظر تصدیق کے دوران RAM کا استعمال بہت بڑھا سکتا ہے

- **مشاہدہ کرنے والا:** Tommaso + Claude
- **سیاق و سباق:** `skills` CLI (`vercel-labs/skills`) کے ذریعے `millionco/react-doctor` سے `improve-threejs` اسکل انسٹال کرنا۔
- **حیرت کی بات کیا تھی:** `npx skills add <repo> --skill <name> --agent codex` اور `--agent cursor` دونوں `.agents/skills/<name>/` میں لکھتے ہیں، نہ کہ `.codex/skills/` یا `.cursor/skills/` میں۔ `AGENTS.md` ریپو کی سطح پر `.agents/` ڈائریکٹری کی ممانعت کرتا ہے اور `.gitignore:29` اسے نظرانداز کرتا ہے، اس لیے دونوں کاپیاں خاموشی سے غیر ٹریک شدہ رہ جاتی ہیں۔ صرف `--agent claude-code` متوقع `.claude/skills/` میں لکھتا ہے۔ الگ سے، دستاویز میں دی گئی کوما سے جدا شکل (`--agent claude-code,codex,cursor`) "Invalid agents" کے ساتھ ناکام ہو جاتی ہے اور کچھ بھی انسٹال نہیں کرتی، حالانکہ ہر نام اکیلے میں درست ہے۔
- **اثر:** انسٹال کامیابی کی اطلاع دیتا ہے جبکہ تین ٹول چین کاپیوں میں سے دو ایسی جگہ جا پہنچتی ہیں جو کبھی کمٹ نہیں ہوگی، اس لیے نئے کلون کے بعد Codex اور Cursor میں یہ اسکل خاموشی سے موجود نہیں ہوتی۔ کوما والی شکل ایسا بے اثر انسٹال بھی کر سکتی ہے جو کامیاب دکھائی دیتا ہے۔
- **موجودہ تدارک:** ریپوزٹری اب `.agents/skills` کو اپنے کینونیکل سورس کے طور پر ٹریک کرتی ہے اور `yarn ai-workflow:sync` سے Claude کی کاپیاں تیار کرتی ہے۔ `.agents` کی سابقہ ممانعت اور اسے نظرانداز کرنے کا قاعدہ ہٹا دیا گیا ہے۔ نئی اسکلز کو تین آزاد روٹ ڈائریکٹریوں میں کاپی نہ کریں؛ اسکل شامل کرنے کے بعد تیار کردہ کاپیوں کی برابری اور ایپ کیٹلاگ کی جانچ کریں۔
