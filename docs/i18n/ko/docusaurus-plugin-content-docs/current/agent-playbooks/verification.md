# 검증

검사는 변경된 동작과 남아 있는 불확실성을 기준으로 고르세요. 같은 최종 상태에 대해 이미 성공한 증거는 재사용하고, 관련 편집이 있었거나 실패했다면 다시 실행하세요. CI, 릴리스, 사용자가 명시한 요구 사항은 그대로 적용됩니다.

| 변경                                      | 적절한 검사                                                                                                         |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 문장/주석/포맷만 변경                     | diff, 참조, 관련 생성기 확인. 앱 빌드는 하지 않음                                                                   |
| AI 워크플로 소스/설정                     | `yarn ai-workflow:sync`, `yarn ai-workflow:check`, `yarn ai-workflow:test`. 컨텍스트가 바뀌었다면 LLM 인덱스 재생성 |
| 독립된 헬퍼나 스크립트                    | 해당 부분에 집중한 호출/픽스처, 그리고 영향받는 코드의 구문 또는 타입/린트 검사                                     |
| 공유 런타임, 의존성, 빌드, 통합 관련 변경 | 영향받는 부분에 집중한 검사와 아래의 관련 빌드/타입/린트 검사                                                       |
| CSS/테마/레이아웃만 변경                  | 선택한 브라우저에서 영향받는 라우트/뷰포트/테마 확인. 임포트, 에셋, CSS 처리가 바뀌었다면 빌드                      |
| React 상태/이펙트/성능                    | 영향받는 동작과 해당되는 React 지침. 진단으로 구체적인 우려를 해소할 수 있을 때 Doctor 실행                         |

## 프로젝트 검사

- `yarn build:verify`는 영향받는 워크스페이스를 골라 빌드합니다. 범위를 이미 알고 있다면 `yarn build:about`, `yarn build:chain`, `yarn build:stats-monitor`, `yarn docs:build:verify` 중 하나를 사용하세요.
- `yarn build`는 모든 문서 로케일을 포함한 about/문서 프로덕션 빌드 전체를 의도적으로 실행합니다. 릴리스 전반을 검증하거나 그만한 범위가 필요한 변경에 사용하세요.
- `yarn lint`, `yarn typecheck`, `yarn format:check`는 저장소의 기존 게이트를 담당합니다. 스크립트 하나를 좁게 수정했다면 먼저 그 스크립트에 집중한 구문/픽스처/포맷 검사를 사용하세요.
- 매니페스트/락 파일 변경에는 `corepack yarn install`, `yarn deps:check-pinned`, `yarn deps:check-hardened`가 필요합니다. `yarn knip`은 의존성/임포트에 대한 권고성 검사입니다.
- 문서 번역 검사는 [translations.md](translations.md)에 정리되어 있습니다. 범위가 좁은 문서 변경에는 대량 번역 작성기를 실행하지 마세요.

## 브라우저 증거와 소유권

작고 독립된 브라우저 변경에는 Chrome을 사용하세요. 공유 CSS/레이아웃/반응형, 브라우저마다 다르게 동작하는 API, 광범위한 상호작용, 릴리스, 또는 명시적인 크로스 브라우저 기준이 걸려 있다면 Firefox와 WebKit을 추가하세요. 영향받는 모바일 레이아웃과 터치 동작도 포함하세요. 뷰포트 크기를 바꾸는 것만으로는 터치 에뮬레이션이 되지 않습니다. 예시가 존재한다고 가정하지 말고 소스를 보고 실제 라우트와 콘텐츠를 고르세요.

`playwright-cli`는 `./scripts/pw-session.sh`를 통해 사용하세요. 머신 전체에서 활성 브라우저는 하나뿐입니다. 선택한 엔진은 순차적으로 실행되며, 자신이 소유한 각 세션은 실패한 경우에도 정확히 그 세션만 닫힙니다. 권한을 받은 호출자 소유 세션은 닫지 말고 재사용하세요. 전역 브라우저 정리를 사용하거나 소유자가 불분명한 서버를 중지하지 마세요. 문서만 다루는 작업에는 브라우저나 서버가 필요하지 않습니다.

성능 작업에서는 같은 흐름을 동일한 뷰포트, 콘텐츠, 네트워크/CPU 설정, 빌드 모드, 측정 오버헤드 조건에서 비교하세요. 관찰한 사실과 추정되는 원인을 구분하세요. 이런 측정이 실제 요청에 대한 답이 될 때 프로파일 스킬을 사용하세요.

## 최종 증거

무거운 검증은 에이전트 하나가 맡습니다. 실행 중인 작업 부하를 확인하고, 설치, 빌드/전체 테스트 스위트, Doctor, Android/Electron 작업, 브라우저 프로파일링은 한 번에 하나씩 순서대로 실행하세요. 실행한 명령과 결과, 구체적인 한계를 보고하세요. 데이터가 없거나 엔진을 건너뛴 것은 통과한 결과가 아닙니다. 도구 픽스처는 형식과 동작 방식을 검증할 뿐, 앱의 종단 간 탐색이나 모델의 판단 품질을 검증하지는 않습니다.

## 자동 React 검사

`yarn agent:verify`는 선택된 빌드를 실행한 뒤 `yarn doctor:check`와 `yarn perf:check`를 실행합니다. `perf:check`에는 수집기 호환성 검사와 의도적 회귀 셀프 테스트가 포함되어 있으므로, CI와 에이전트 검증 경로 모두 별도의 `perf:test` 실행이 필요하지 않습니다. 고정된 브라우저 도구는 `yarn perf:install`로 한 번만 설치하세요(Linux CI에서는 `--with-deps`). 관련된 전체 실행을 마친 뒤 특정 부분만 다시 실행할 때는 대상/시나리오 필터를 사용하세요. 시나리오 예산은 `scripts/react-perf/config.mjs`에 명시되어 있습니다. 근거 있는 기준선 변경을 고려하기 전에 증거를 보존하고 회귀부터 고치세요. 일반 프로덕션 빌드에는 Bippy가 포함되지 않으며, 별도의 `build:profile:*` 명령이 공식 React 프로파일링 계측을 제공합니다.

about의 `apps-search` 시나리오는 글자마다 커밋된 URL/입력 값에 맞춰 진행 속도가 조절됩니다. 이 시나리오가 통과했다는 결과는 그 커밋된 쿼리 시퀀스를 보장할 뿐, 빠르게 타이핑할 때의 반응성까지 보장하지는 않습니다. 글자 누락이나 입력 반응성을 평가할 때는 별도의 빠른 입력 재현을 사용하세요.
