# Bitsocial과 Bluesky

[Bluesky](https://bsky.app/)는 Bluesky Social PBC가 설계한 [AT Protocol](https://atproto.com/) 위에
만들어진 마이크로블로깅 앱입니다. 이 프로토콜은 소셜 네트워크를 별개의 서비스로 나눕니다. 개인
데이터 서버가 계정을 호스팅하고, 릴레이가 이를 하나의 스트림으로 모으며, AppView가 그 스트림을
색인해 사람들이 보는 타임라인과 스레드로 만듭니다. AT Protocol 문서는 계정 데이터가 "P2P 모델과
달리" 호스트 서버에 저장된다고 설명합니다([개요](https://atproto.com/guides/overview)).

## AT Protocol의 동작 방식

- **서버에 있는 저장소.** 모든 게시물, 좋아요, 팔로우는 작성자의 서명된 저장소(repository)에 담긴
  레코드이며, 이 저장소는 개인 데이터 서버(PDS)에 호스팅됩니다. 기본 서버는 Bluesky가 운영하지만,
  누구나 자신의 서버를 호스팅할 수 있습니다.
- **릴레이.** 릴레이는 모든 PDS를 구독하고 변경 사항을 하나의 스트림, 즉 파이어호스로 다시
  내보냅니다. 2025년 프로토콜 업데이트 이후로는 모든 저장소를 보관하지 않게 되어 운영 비용이 크게
  줄었습니다([Sync v1.1](https://atproto.com/blog/relay-updates-sync-v1-1)).
- **AppView.** AppView는 파이어호스 전체를 색인해 타임라인, 완전한 답글 스레드, 각종 집계, 검색을
  제공합니다. 네트워크에서 자원을 가장 많이 쓰는 부분입니다.
- **신원.** 계정은 DID입니다. 보통은 하나의 전역 디렉터리에 등록되는 `did:plc`이고, 도메인에 묶인
  `did:web`일 수도 있습니다. DID 문서에는 계정의 핸들, 서명 키, 현재 서버가 적혀 있습니다. 서명 키는
  PDS가 보유하며, `did:plc`에서는 사용자가 교체 키(rotation key)를 보유할 수도 있어 기존 호스트의
  도움 없이 이전할 수 있습니다([신원 가이드](https://atproto.com/guides/identity)).
- **핸들.** 핸들은 `alice.bsky.social`이나 사용자가 소유한 도메인 같은 DNS 이름이며, DID와 대조해
  검증됩니다.
- **모더레이션.** 호스팅과 도달 범위는 별개의 계층입니다. 누구나 라벨러를 운영할 수 있고 사용자는
  여러 라벨러를 겹쳐 쓸 수 있지만([모더레이션 가이드](https://atproto.com/guides/moderation)),
  Bluesky 앱은 항상 Bluesky 자체의 모더레이션을 적용합니다. 작성자는 자기 게시물에 누가 답글을 달 수
  있는지 제한하고 답글을 숨길 수 있습니다.

## 차이점

### 서버인가, 피어인가

Bluesky의 데이터는 서버에 있습니다. PDS가 각 계정을 호스팅하고, 릴레이가 파이어호스를 나르며,
AppView가 클라이언트에 표시될 내용을 제공합니다. 브라우저는 이 서비스들의 HTTP 클라이언트일 뿐
피어가 되지는 않습니다. Bitsocial에서는 커뮤니티의 노드와 그 커뮤니티를 읽는 피어가 콘텐츠를
제공하며, 웹 앱이 자체 P2P 노드를 실행할 수 있습니다. [브라우저 피어 투 피어](/browser-p2p/)를
참고하세요.

### 전역 뷰인가, 커뮤니티인가

AT Protocol은 하나의 전역 뷰를 전제로 설계되었습니다. AppView가 모든 답글을 보기 때문에 스레드와
검색이 완전합니다. Bitsocial에는 전역 색인이 없습니다. 각 커뮤니티가 자신의 상태를 발행하고, 앱이 그
위에 콘텐츠 발견 기능을 만듭니다. [콘텐츠 발견](/content-discovery/)을 참고하세요.

현재 Bluesky에는 공개 게시물을 위한 커뮤니티 객체가 없습니다. 2026년 6월 Bluesky는 일부 공개
범위에서 승인을 거쳐야 게시할 수 있는
[네이티브 커뮤니티를 발표](https://bsky.app/profile/alexbenzer.com/post/3mnxh6mmlxk2k)했지만, 2026년
10월까지 출시되지 않았습니다. Bitsocial에서는 커뮤니티가 핵심 객체이며, 커뮤니티의 노드가 게시물을
수락하거나 거부합니다.

### 스팸 방지

Bluesky는 자사 서버의 속도 제한, 릴레이의 신규 호스트 제한, 자동 탐지, 사람의 검토, 라벨로 스팸에
대응하며, 작성자는 답글을 제한할 수 있습니다. 게시물이 받아들여지기 전에 무엇을 통과해야 하는지
정하는 커뮤니티 단위의 관문은 없습니다. Bitsocial에서는 각 커뮤니티가 자체 챌린지를 고릅니다.
[맞춤형 스팸 방지 챌린지](/custom-challenges/)를 참고하세요.

### 누가 키를 쥐고 있는가

Bluesky 자체 서버에 있는 계정은 비밀번호로 로그인하며, 그 서버가 계정의 서명 키를 수탁
보관합니다([Kleppmann 외](https://arxiv.org/abs/2402.03239)). Bluesky의 한 프로토콜 엔지니어에
따르면
[대부분의 계정에는 독립적으로 통제되는 교체 키가 없습니다](https://whtwnd.com/bnewbold.net/3lbvbtqrg5t2t).
Bitsocial 신원은 사용자의 앱이 생성하고 보유하는 키페어입니다.

### 인프라 운영

개인 서버는 저렴합니다. [참조 PDS](https://github.com/bluesky-social/pds)는 사용자 20명까지 RAM
1GB를 권장합니다. 네트워크 전체를 다루는 독립 AppView는 큰 프로젝트입니다. 2025년에 만들어진 한
AppView는 [월 약 200달러가 들었고](https://whtwnd.com/futur.blue/3ls7sbvpsqc2w), 대부분이 16TB 저장
공간 비용이었습니다. Bitsocial에는 복제해야 할 전역 색인이 없고, 커뮤니티 노드는 일반 소비자용
하드웨어에서 돌아갑니다.

## 비교

| 질문             | Bluesky (AT Protocol)                                                 | Bitsocial                                                                     |
| ---------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 분류             | 전역 색인을 갖춘 연합 서버                                            | P2P 커뮤니티 네트워크                                                         |
| 신원             | DID, 서명 키는 보통 서버가 보유                                       | 사용자와 커뮤니티를 위한 Ed25519 키페어                                       |
| 게시물 저장 위치 | 개인 데이터 서버에 있는 작성자의 저장소                               | 커뮤니티 소유자의 노드와, 그 커뮤니티를 읽고 시드하는 피어                    |
| 온라인 유지 주체 | PDS 호스트, 릴레이, AppView, 기본적으로 Bluesky가 운영                | 커뮤니티 소유자 노드와 보조 시더                                              |
| 커뮤니티         | 공개 게시물용은 아직 없음(2026년 발표)                                | 자체 노드가 게시물을 수락하거나 거부하는 일급 객체                            |
| 스팸 방지        | 서버 속도 제한, 자동 탐지, 라벨, 답글 제어                            | 게시물이 받아들여지기 전에 거치는 커뮤니티별 챌린지                           |
| 모더레이션       | 겹쳐 쓸 수 있는 라벨러, Bluesky 앱은 항상 Bluesky의 모더레이션을 적용 | 커뮤니티 소유자가 자기 커뮤니티를 모더레이션하고, 무엇을 보여줄지는 앱이 선택 |
| 이름             | DID와 대조해 검증되는 DNS 핸들                                        | 키로 해석되는 `.bso` 및 `.eth` 이름                                           |
| 브라우저         | PDS와 AppView의 HTTP 클라이언트                                       | 일반 브라우저 탭 안에서 동작하는 P2P 노드                                     |
| 주요 절충        | 완전한 전역 스레드와 검색, 그러나 집계에 무거운 서버가 필요           | 무거운 전역 색인은 없지만 네트워크 전체를 완전히 보는 뷰도 없음               |
